Phase 4: Security and Credentials

Azure Service Principal and RBAC Credentials

Page 06 · Workflow Implementation
💡 Beginners Guide: What are RBAC and Service Principals?

1. What is RBAC? (Role-Based Access Control):
Think of a hotel keycard. When you check in, your keycard unlocks your hotel room door and the elevator, but it will never unlock the manager's office or the penthouse suite. In Azure, RBAC gives software a specific keycard role (here, Storage Blob Data Contributor). This lets GitHub Actions upload website files to the $web folder, but strictly prevents it from touching virtual machines, databases, or billing.

2. What is a Service Principal?
Humans log into Azure with an email, password, and two-factor phone code. But GitHub Actions is an automated robot running in the cloud; it has no phone to receive a text message. A Service Principal is an automated digital employee badge created specifically for software, giving it a secure Client ID and Client Secret so it can log into Azure safely without human intervention.

Follow these two steps to create GitHub's automated login badge and assign its upload permissions:

1
Register App in Microsoft Entra ID:
1. In Azure Portal top search bar, type Microsoft Entra ID and select it.
2. Under Manage, click App registrations > + New registration.
3. Name: sp-github-cicd-deploy.
4. Click Register. Copy the Application (client) ID and Directory (tenant) ID.
2
Generate Client Secret & Assign IAM Role:
1. In sp-github-cicd-deploy, click Certificates & secrets > + New client secret > click Add. Copy the Secret Value immediately.
2. Navigate to your storage account > click Access Control (IAM) > + Add role assignment.
3. Select role Storage Blob Data Contributor > assign to member sp-github-cicd-deploy > click Review + assign.
SDK-Auth JSON Output
{ "clientId": "xxxx-xxxx-xxxx", "clientSecret": "xxxx-xxxx-xxxx", "subscriptionId": "xxxx-xxxx-xxxx", "tenantId": "xxxx-xxxx-xxxx" }
⚠️ Critical Security Rule
NEVER commit this JSON payload or your clientSecret to git. Anyone with this JSON can access your Azure resources.
Production Best Practice
In enterprise setups, teams use Workload Identity Federation (OIDC) to let GitHub assume roles without long-lived client secrets.
Phase 5: Automation Configuration

Secrets and GitHub Actions Workflow

Page 07 · Automated Pipeline Testing

Step 4a: Add Repository Secrets

1
In GitHub: Navigate to Settings, click Secrets and variables, then select Actions.
2
Secret 1: AZURE_CREDENTIALS. Paste the full Service Principal JSON output.
3
Secret 2: AZURE_STORAGE_ACCOUNT. Paste your Storage Account name.

Step 4b: Commit and Push

git add .github/workflows/deploy.yml git commit -m "ci: add automated Azure deployment workflow" git push origin main
Pipeline Logic
On every push to main: Spin up an Ubuntu runner, authenticate via Azure Service Principal, and batch-upload files into $web using Azure CLI.
.github/workflows/deploy.yml
# .github/workflows/deploy.yml name: Deploy Static Website to Azure on: push: branches: [ main ] jobs: build-and-deploy: runs-on: ubuntu-latest steps: - name: Checkout repository code uses: actions/checkout@v4 - name: Log in to Azure via Service Principal uses: azure/login@v2 with: creds: ${{ secrets.AZURE_CREDENTIALS }} - name: Upload files to Azure Blob Storage ($web) uses: azure/CLI@v2 with: inlineScript: | az storage blob upload-batch \ --account-name ${{ secrets.AZURE_STORAGE_ACCOUNT }} \ --auth-mode login \ --destination '$web' \ --source . \ --overwrite true \ --pattern "*"

Troubleshooting: What to do if the workflow fails
  • AuthorizationPermissionMismatch: Ensure Service Principal has Storage Blob Data Contributor on the Resource Group.
  • Invalid credentials: Ensure entire JSON block was pasted into AZURE_CREDENTIALS with no missing braces.
  • Destination container not found: Verify static website hosting is enabled so $web exists.
  • Workflow not triggering: Verify path is .github/workflows/deploy.yml (lowercase, plural workflows).
